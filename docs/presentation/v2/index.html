我们面对的真实场景

  • 业务同事有想法、有工具需求，但不会写代码，只能私下找认识的开发
  • 开发同事各自为战，不知道需求池里还有什么，重复功能被做多遍
  • 小项目缺少统一仓库、PR、CI，交付质量与过程不可见
  • 上线后问题通过聊天反馈，没有工单、没有负责人，迭代很快断档

以下 5 页逐条展开「痛在哪 / 平台怎么解」

① 口头需求 · 找不到统一入口

痛点

  • 需求散落在 IM、会议、口头，无法检索、无法排期
  • 提出方说不清验收标准，开发反复对齐浪费时间
  • 管理者看不到「谁在等什么」，资源无法统筹
→

aiManager 方案

  • 简化发布表单：非技术同事也能发布结构化需求单
  • 需求进入公开需求池，卡片展示状态与标签
  • 需求沟通时间线、共同需求人，过程留痕

面向小白：引导文案与「下一步」提示，降低发布门槛

② 有能力的人 · 却不知道有什么可做

痛点

  • 开发只服务「熟人队列」，池外需求长期积压
  • 技能与兴趣不匹配，认领效率低
  • 新需求没有触达机制，信息孤岛
→

aiManager 方案

  • 需求池 + 标签：按能力方向浏览与筛选
  • 标签订阅：匹配的新需求定向通知
  • 认领前可见背景与沟通记录，减少误领

让「愿意做的人」主动看见任务，而不是只靠私下指派

③ 重复造轮子 · 同一功能多套实现

痛点

  • 同一业务需求被多个小组并行实现
  • 缺少「谁在做」的权威状态，冲突发现太晚
  • 维护成本随副本数量线性上升
→

aiManager 方案

  • 业务侧需求单唯一化，一个需求对应一条主线
  • 先到先得原子认领：并发认领不会重复开工
  • 认领后自动关联项目与仓库， ownership 清晰

README 核心表：「多人重复开发相同功能 → 认领锁 + 唯一需求单」

④ 协作与发布 · 缺少规范底座

痛点

  • 临时目录、手工拷代码，无版本、无评审
  • 没有统一 CI，上线质量靠个人习惯
  • 组织难以审计「谁改了什么、何时发布」
→

aiManager 方案

  • 认领后按模板自动创建 Gitea 仓库
  • 标准流程：分支 → PR → 评审 → merge
  • Gitea Actions（act_runner） 构建/测试/发布，状态回写平台

平台通过 Gitea API + Webhook 把 PR、流水线与业务状态打通

⑤ 交付之后 · 反馈石沉大海

痛点

  • 用户问题发在群里，没有负责人、没有优先级
  • 开发已转其他项目，历史上下文丢失
  • 迭代无法闭环，工具逐渐无人维护
→

aiManager 方案

  • 平台内提交反馈，自动在对应仓库创建 Issue
  • 需求沟通与成果中心（README / 教程 / 下载）集中呈现
  • Issue 驱动再次 PR，形成发布 → 反馈 → 迭代 闭环

全链路 E2E（68 项）覆盖：注册 → 建仓 → PR → CI → 反馈 Issue

延伸方案 · 让员工用 AI 安全协作

新痛点（AI 时代）

  • AI 能写代码，但碰不到内部需求与 Git 规范
  • 把管理员 Token 交给客户端风险极高
  • 自动 commit/push 缺少确认与审计
→

aiManager 方案

  • Agent API + 员工 PAT（scope 分级 + 审计）
  • 远程 MCP 查需求/反馈；本地 MCP / aim CLI 安全 Git
  • safe-git：工作区/分支限制；写操作需 MCP 确认或 aim approve

原则：平台给身份与上下文；代码 push 走员工自己的 Gitea 凭证，不下发服务端 Token

小结：一套平台，解决五条协作断点

对业务同事

会填表就能发需求、看进度、提反馈；不必认识「哪个开发」。

对开发同事

需求池可见、认领有锁、仓库与 CI 开箱即用；AI 工具可接入但不越权。

对团队 / 运维

Docker Compose 单机部署；Caddy 统一入口；文档与 E2E 保障可运维。
